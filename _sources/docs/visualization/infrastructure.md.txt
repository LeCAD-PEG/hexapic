# How it works

The viewer has two parts: a Python server, `tools/viz/hexapic_viz.py`, and a
web app in `tools/viz/web/`. The app reads only frames. The server either
builds the frames from the openPMD series or serves the frames that HEXAPIC
wrote itself.

## Frames

There is one binary frame per output step. A frame consists of a JSON header
followed by the arrays:

```text
b"HXLF"  u32 version  u32 H  JSON header (H bytes)  zero padding to 8
the arrays, each at header["arrays"][i]["offset"] from the padded end, 8-aligned
```

Each array is stored as 16-bit values scaled between its minimum and its
maximum. Phase spaces store $\log(1 + n)$ of the counts. The header describes
an array as `{"name", "dtype": "u16", "shape": [rows, cols], "offset", "min",
"max", "log"}`.

A stored value $q = 0$ means NaN, which is also used for an empty
phase-space bin. Any other value decodes to

$$
v = v_\mathrm{min} + \frac{q - 1}{65534}\,(v_\mathrm{max} - v_\mathrm{min}) .
$$

With `[output] frame_bits = 8` the values are stored in 8 bits. The frames
are then half the size and have 255 levels. This setting applies both to the
frames written during a run and to the frames the server builds from the
series. The browser widens them to 16 bits when it reads them.

HEXAPIC writes the same format when it runs with `[output] live`. The code is
in `source/io/live_frames.hpp`.

## The server

The server converts an openPMD series into frames once and stores them in a
cache next to the series, `<output>/.hexapic_viz`. If it cannot write there,
it uses `~/.cache/hexapic_viz`. The conversion uses as many processes as
there are cores, and steps that are not built yet are built on demand. The
cache stays valid as long as the series does not change. Answering a request
then only means reading the arrays at their offsets in a file.

| Endpoint | Returns |
|---|---|
| `api/runs` | The listing for the explorer |
| `api/meta` | The run: its quantities, its steps and their ranges over the run |
| `api/frames?a=phi,...&s=0,200,...` | Several arrays at several steps, gzipped |
| `api/raw?q=phi&s=10000` | One array with the values of the series, as `.npy` |
| `api/probe` | The values at a point over the run |
| `api/region` | The statistics of a rectangle over the run |
| `api/tstat` | The mean, minimum, maximum or standard deviation at every point over a range of steps |
| `api/video/...` | Receives the frames of a video and passes them to `ffmpeg` |

## The app

The app loads every step of the displayed quantities in the background. It
requests only the arrays that the open views need, eight steps per request
over one connection. It starts with the displayed step and continues outward
from it. The app keeps at most 1.5 GB. Beyond that it drops the steps
farthest from the displayed one.

When the step changes, the app redraws only what changed, which is the
textures of the images and the lines of the plots. The axes are rebuilt only
when their size or range changes.
